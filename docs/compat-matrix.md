# MKV -> MP4 compatibility matrix (empirical)

Tool: `ffmpeg version 8.1.1-full_build-www.gyan.dev` (the exact build that will be shipped).
Evidence: `tests/compat_results.json` (harness `tests/compat_test.py`) and `tests/compat_results2.json`
(harness `tests/compat_test2.py`, outputs in `tests/compat_out/t2`, extra samples in `tests/media/extra`).
All samples are synthetic (generated by the `tests/make_*.py` scripts); no real disc PGS/VobSub files were tested.

"Decode OK" = `ffmpeg -i out.mp4 -map 0 -f null -` exits 0 with an empty error log (subtitles: `ffprobe -show_frames`
returns events). It proves the file is valid for FFmpeg-based players (mpv, VLC, PotPlayer, MPC + LAV); it does
**not** prove the Windows "Media Player / Films & TV" app or phones/TVs can play it. That column is marked separately.

## 3. Recommended per-stream policy

Probe first: `ffprobe -v error -show_streams -show_format -show_chapters -of json in.mkv`.
Build the command with **explicit `-map 0:<index>` per kept stream** (never `-map 0`), output to a temp name, then
rename. Never write to the source path; refuse if output path == input path.

| Input stream | Action | Arguments (N = output stream index of that type) |
|---|---|---|
| h264, av1, vp9, mpeg2video, mpeg4, mjpeg, ffv1 video | copy | `-map 0:i -c:v:N copy` |
| hevc video | copy + Apple-friendly tag | `-map 0:i -c:v:N copy -tag:v:N hvc1` |
| vp8, theora, msmpeg4v3, wmv*, prores, h263, any "Could not find tag" video | cannot copy -> re-encode (lossy, warn user) | `-c:v:N libx264 -crf 16 -preset slow -pix_fmt yuv420p` (10-bit or HDR source: `libx265 -crf 18 -preset medium -pix_fmt yuv420p10le -tag:v:N hvc1`); source color_primaries/color_trc/colorspace are passed through; original stream also saved as a `.mkv` sidecar |
| aac, mp3, mp2, ac3, eac3, dts, flac, alac, opus | copy | `-c:a:N copy` |
| vorbis, pcm_* | copy (works), flag "low device compatibility" in the report | `-c:a:N copy` |
| truehd | copy needs experimental | add global `-strict experimental` (only when a TrueHD track is mapped); flag low compatibility |
| wavpack, tta (lossless) | re-encode losslessly | `-c:a:N flac` |
| wmav2, speex, other impossible lossy | re-encode | `-c:a:N aac -b:a:N 256k` |
| srt | convert in MP4 | `-c:s:N mov_text` (sidecar optional) |
| ass/ssa | convert in MP4 **and** keep original | `-c:s:N mov_text` + sidecar `ffmpeg -i in.mkv -map 0:i -c:s copy "<name>.<n>.<lang>.ass"` + dump fonts |
| webvtt | convert in MP4 + sidecar | `-c:s:N mov_text` + `-map 0:i -c:s copy "<name>.<n>.<lang>.vtt"` |
| dvd_subtitle | copy into MP4 (FFmpeg players render it) **and** sidecar | `-c:s:N copy` + `-map 0:i -c:s copy -f matroska "<name>.<n>.<lang>.mks"` |
| hdmv_pgs_subtitle | sidecar only (cannot enter MP4) | `-map 0:i -c:s copy "<name>.<n>.<lang>.sup"` |
| other unknown subtitle | try `-c:s:N mov_text` if text, else sidecar `.mks` | `-map 0:i -c:s copy -f matroska x.mks` |
| image attachment (shown as video + `attached_pic`) | cover art | `-map 0:i -c:v:N copy -disposition:v:N attached_pic` (also do NOT add `-tag:v`/encoder options to it) |
| font / other `attachment` stream | do not map; dump | `-dump_attachment:<i> "<abs dir>\<filename>"` placed before `-i in.mkv`, in a separate run ending with `-f null -` (rc 0); then check the file exists |
| data streams | chapter text tracks are rewritten as chapters, tmcd via `-write_tmcd 1`; anything else saved as a sidecar (`.mks`, or `.mov` for fragmented input) | `-map 0:i -c copy -f matroska x.<i>.<lang>.mks` |

Per kept stream, always add:
- Title: `-metadata:s:<type>:N handler_name=<MKV title>` (only when the MKV has a title; the default `udta/name` write stays).
- Language: if the MKV language is a valid 3-letter ISO 639-2 code it is copied automatically. If it is BCP-47
  (`zh-CN`, `zh-Hans`, `pt-BR`, ...), map the primary subtag to ISO 639-2 (`zh`->`chi`, `en`->`eng`, `ja`->`jpn`,
  `pt`->`por`, ...) and pass `-metadata:s:<type>:N language=<code>`; record the original in the sidecar.
- Disposition: inherited automatically (default/forced/comment/hearing_impaired/visual_impaired verified); no flags needed.

Global options:
```
-map_metadata 0 -map_chapters 0 -movflags +faststart
```
Never `+use_metadata_tags` (kills iTunes tags and cover art). Instead, when the MKV has any global tag that is not
one of title/artist/album/date/comment/genre/composer/copyright/description/encoder, or any stream title/language
that MP4 cannot represent exactly, also write:
```
ffmpeg -i in.mkv -f ffmetadata "<name>.metadata.txt"
```
plus a JSON dump of `ffprobe -show_streams -show_format -show_chapters` (stream-level tags such as BCP-47 languages
and original titles are not in ffmetadata).

### Reference command (multi.mkv: h264 + aac/ac3/flac + srt/ass/vtt + ttf + jpg cover + chapters)

Verified working (first command run exactly as shown, by a one-off script not kept in the repository; sidecar/dump commands verified individually in the harnesses):
```
ffmpeg -hide_banner -nostdin -y -i multi.mkv ^
  -map 0:0 -map 0:1 -map 0:2 -map 0:3 -map 0:4 -map 0:5 -map 0:6 -map 0:8 ^
  -c copy -c:s mov_text -disposition:v:1 attached_pic ^
  -metadata:s:a:0 handler_name=日语 -metadata:s:a:1 "handler_name=English 5.1" -metadata:s:a:2 handler_name=国语 ^
  -metadata:s:s:0 handler_name=简体中文 -metadata:s:s:1 "handler_name=English Signs (ASS)" -metadata:s:s:2 "handler_name=WebVTT 日本語" ^
  -map_metadata 0 -map_chapters 0 -movflags +faststart out.tmp.mp4
ffmpeg -i multi.mkv -map 0:5 -c:s copy "multi.2.eng.ass"
ffmpeg -i multi.mkv -map 0:6 -c:s copy "multi.3.jpn.vtt"
ffmpeg -dump_attachment:t:0 "fonts\testfont.ttf" -i multi.mkv -f null -
ffmpeg -i multi.mkv -f ffmetadata "multi.metadata.txt"
```
Result: all A/V decode clean, 3 mov_text tracks with languages + forced flag, cover in `covr` byte-identical,
3 chapters with Chinese titles, title/artist/date/comment as iTunes atoms, faststart layout.

## 5. FLV and MPEG-TS input (1.1.0)

Samples: `tests/make_flv_ts_samples.py` -> `tests/media/flv_ts/` (FLV h264+aac, enhanced FLV with HEVC and AV1,
FLV cut at 60 %, TS h264 + 3 AAC with languages, TS HEVC 10-bit + 2 AAC with `repeat-headers`, TS cut at 60 %,
TS whose audio starts 0.279 s after the video at ~1.47 s, 192-byte-packet M2TS h264 + AC-3, two TS files joined
with a 5000 s timestamp jump). All are converted by stream copy and pass `tests/e2e_run.py cli flv_ts`.

What changes compared with MKV:

| Item | Finding (ffmpeg 8.1.1) | What the tool does |
|---|---|---|
| AAC in TS is ADTS | `-v verbose` shows `Automatically inserted bitstream filter 'aac_adtstoasc'` for the MP4 muxer | nothing extra for the conversion; verification hashes the TS side through `aac_adtstoasc` |
| H.264/HEVC in TS are Annex B | MP4 stores length-prefixed NALs, so a plain packet hash never matches (see below) | normalised hash, see below |
| HEVC with `-tag hvc1` | the MP4 muxer moves in-band VPS/SPS/PPS out of the samples into `hvcC` (first packet 10045 bytes in TS vs 10047 after `hevc_mp4toannexb`, parameter sets in a different position) | parameter sets are excluded from the stream hash and compared separately (first packet) |
| AV1 in enhanced FLV | FLV packets start with a temporal delimiter OBU (`12 00`), MP4 samples do not | both sides hashed through `filter_units=remove_types=2\|15` |
| H.264/HEVC/AAC in FLV | stored like MP4 (AVCC/hvcC, raw AAC): packet hashes match byte for byte | plain hash |
| TS start time | TS starts at ~1.4 s (audio 1.4453, video 1.4667); the MP4 starts at 0 (audio 0.000, video 0.021) | relative start of every track vs the first video track is checked (tolerance 1 frame + 2 ms); passes on all samples including the late-audio TS (+0.279 -> +0.278) |
| TS timestamp jump | `ffprobe` reports a format duration of 1:23:28 for the joined 18 s file; ffmpeg logs `timestamp discontinuity` and rebases | the duration check is skipped and the report explains that the nominal duration is wrong |
| Cut TS | no error message from the demuxer; file size not a multiple of the packet size; the last video PES is partial and decodes with `error while decoding MB` | detected from the packet alignment; the input is cut (subfile) at the last video packet with the payload-start flag, so the half frame is dropped; decode check at the end is clean |
| Cut FLV | demuxer logs `Packet corrupt` / `Invalid NAL unit size` for the last tag | detected from the last `PreviousTagSize`; `-fflags +discardcorrupt` drops the half tag (same flag used when hashing) |
| Data streams in TS/FLV (SCTE-35, AMF data, ...) | Matroska cannot hold several of them, so a sidecar would fail | ignored with a line in the report |

### Verification method for Annex-B sources

Requirement: still bit-exact for the coded picture data, and fast enough for multi-hour recordings.

- TS side: `-c copy -bsf filter_units=remove_types=7|8|9` (H.264) or `32|33|34|35` (HEVC). `filter_units` only splits
  the access unit into NAL units and writes them back with a uniform start-code layout; it does not decode or
  rewrite slice data. Parameter sets and access unit delimiters are removed.
- MP4 side: `h264_mp4toannexb` / `hevc_mp4toannexb` followed by the same `filter_units`.
- Both go to the `streamhash` muxer (MD5 of all packet payloads); the MD5s must be equal. On a mismatch the same
  filters are applied to `framemd5` to find the first differing packet (same tolerance rules as for MKV: tail-only
  differences of a cut recording are a warning).
- Parameter sets: the SPS/PPS(/VPS) NAL units of the first packet are extracted on both sides
  (`filter_units=pass_types=...`, `-frames 1`) and compared as sets; a difference is a warning.

Empirical evidence: on the synthetic samples the normalised MD5s are identical for every H.264/HEVC/AAC/AV1
stream (h264 `ac2464...` = `ac2464...`, hevc `7bd933...` = `7bd933...`), while unnormalised hashes differ;
first-packet parameter sets are byte-identical after normalisation. A full CBS rewrite (`h264_metadata`) also gave
equal hashes for H.264 but not for HEVC (parameter-set relocation), which is why the parameter sets are compared
separately instead. Speed on a 308 MB 1080p60 TS: plain `streamhash` 0.6 s, normalised 1.6 s for each side
(about 190 MB/s); above 8 GB the existing rule (first 3000 packets per track) applies. A decoded-frame hash was
not needed because the payload comparison is exact.

## 6. Audio track export (1.1.0)

Each audio track of the source (not of the MP4, so tracks that had to be re-encoded for MP4 are exported in their
original form) is copied into its own file in `<name>_音轨\`, named `<n>-<title, else language, else 音轨n>.<ext>`
(characters illegal on Windows become `_`, trailing dots/spaces are removed, titles are cut at 80 characters).

| Codec | Container | Why |
|---|---|---|
| AAC, ALAC | `.m4a` (`ipod` muxer, brand M4A) | the format every editor and player opens; TS ADTS is converted automatically (verified) |
| MP3 | `.mp3` (ID3v2.3 tags) | v2.3 is what Windows Explorer shows reliably |
| FLAC | `.flac` | |
| Opus | `.opus` (Ogg) | |
| Vorbis | `.ogg` | |
| PCM little-endian (u8/s16/s24/s32/f32/f64) | `.wav` with `-rf64 auto` | RF64 is used only above 4 GB |
| AC-3 / E-AC-3 | raw `.ac3` / `.eac3` | the raw elementary stream is byte-identical to the track and recognised by its extension by players and by Windows' Dolby decoder; AC-3 inside `.m4a` is rejected by Apple apps and confuses tools that expect AAC/ALAC in `.m4a`. Raw files cannot carry title/language, so these are only in the file name |
| anything else (DTS, TrueHD, MP2, big-endian PCM, ...) | `.mka` | Matroska holds every codec |

Tags: title (also `handler_name` in M4A) and language are written where the container has a field (M4A, MP3, FLAC,
Ogg, WAV `INAM`/`ILNG`, MKA).

Start time and sync: the exported file always starts at the track's first sample. The difference between the
track's start and the first video track's start in the source is written into the report when it is larger than
one video frame ("这条音轨比画面晚 0.500 秒开始，剪辑时请对齐"). Only an offset of 0.1 s or more turns the file's
status into "完成（有提示）" (warn); a smaller one (typically the B-frame delay of about 0.067 s in FFmpeg-made
fragmented MP4s) is still written into the report and the summary but leaves the status at "成功". Keeping the offset inside the file was rejected: an
M4A edit list or a Matroska start timestamp is honoured by FFmpeg-based players but not by every editor, so the
same file would line up in one program and be shifted in another, and the report text could not be right for both.
Implementation detail: `-avoid_negative_ts make_zero` was tried first but it moves the AAC priming packet
(pts -1024) to 0 and drops the edit list (a 5.000 s track became 5.023 s, i.e. 21 ms late); the tool instead uses
`-output_ts_offset -(track start - file start)`, which keeps the priming edit list (5.000 s). MPEG-TS is the
exception: for demuxers with discontinuous timestamps FFmpeg rebases the input to the earliest start among the
streams that are actually mapped, so an audio-only export already starts at the earliest audio track. The offset
for TS is therefore measured from the earliest audio start (and is 0 when a single track is exported on its own);
measuring it from the file start pushed the first packet below 0 and the M4A edit list then cut that much audio
(0.279 s of `ts_start1.4_audio_late.ts`). FLV is not rebased this way (checked with a late-audio FLV).

Verification: every exported file is probed (one audio stream, same codec), its first packet must not lie earlier
than the source track's own first packet relative to the track start (so a priming edit list is fine, a cut start
is an error), its duration is compared with the source track (1 s tolerance: TS durations and Matroska `DURATION`
tags are estimates and differ from the real length by up to about half a second in the samples), and `streamhash` of the exported stream must equal the source track's (TS AAC through
`aac_adtstoasc`). `streamhash` hashes the concatenated payload, so the different packet sizes of WAV do not matter.
Observed limitation: ALAC from an MKV without packet durations loses its last packet in `.m4a` (same behaviour as
the main MP4); up to two missing tail packets are reported as a warning, as for the main conversion.
Observed difference: AAC from an MKV can decode to a few samples more in the `.m4a` (and in the main MP4) than in
the MKV itself, although the packets are identical. Matroska stores timestamps in milliseconds, so the priming and
the last block are rounded (OBS 6-track MKV: first packet `skip_samples` 1008 instead of 1024, last packet duration
1008), and the MKV demuxer trims 16 padding samples at the end that MP4/M4A playback keeps: 384000 samples in the
MKV, 384016 in the MP4 and in every exported `.m4a` (0.33 ms at the end, no effect on sync). TS and MP4 sources
match exactly (385024 = 385024, 384000 = 384000).

A source that is already a normal MP4/MOV (for example a cleanly stopped OBS Hybrid MP4) is not converted; with the
option on, only its audio tracks are exported and a report `<name>.转换报告.txt` is written.
